## Task: BUG-040 — Direct Role Assignment Missing OrganizationMember/WorkspaceMember Records

### Problem

`POST /role-assignments` (Settings → Members → Assign Role) created a `RoleAssignment` row but no `OrganizationMember` or `WorkspaceMember` record. `/context/platform` builds `organizations[]` via `OrganizationRepository.list_for_user()` which joined only on `OrganizationMember`. Users with direct role assignments but no membership records got empty `organizations[]` and were stuck in the onboarding gate.

### Root Cause

`ScopedMembershipService.create_role_assignment()` wrote only to `role_assignments`. The invitation flow (`invitation_repository.add_memberships()`) created the membership records, but the direct assignment path had no equivalent. `list_for_user()` in the repository had no fallback to `role_assignments`.

### Fix 1: Membership Creation on Assignment

**`services/core-service/app/services/scoped_membership_service.py`**

Added `_ensure_memberships_for_assignment(assignment, actor_id)` private method called from `create_role_assignment()` just before the final commit:

- **org scope**: creates `OrganizationMember` if missing (with `role_id` from the assignment)
- **workspace scope**: creates `WorkspaceMember` if missing + `OrganizationMember` for the workspace's org if missing + org-scope `organization_member` `RoleAssignment` if no active org assignment exists for that user (mirrors BUG-030 invitation fix)
- **platform / project / team scope**: no action (these scopes don't need org/workspace membership for the context query)

### Fix 2: Resilient list_for_user

**`services/core-service/app/repositories/organization_repository.py`**

`list_for_user()` now unions two subqueries:
1. `OrganizationMember.organization_id WHERE user_id = ?`
2. `RoleAssignment.scope_id WHERE user_id = ? AND scope_type = "organization" AND status = "active" AND scope_id IS NOT NULL`

The union is used in `WHERE Organization.id IN (...)`. This ensures pre-existing direct-assignment users (no membership records) still see their orgs in context.

Also added `from app.models.user import RoleAssignment` import.

### Fix 3: Backfill Endpoint

**`services/core-service/app/api/v1/system.py`**

Added `POST /system/backfill-memberships` (superuser-only). Iterates all active org-scope and workspace-scope `RoleAssignment` rows, creates missing `OrganizationMember` and `WorkspaceMember` records. Returns `{ created_org_members, created_workspace_members }`.

### Tests

**`services/core-service/tests/test_scoped_membership.py`**

Added 2 new tests:
- `test_direct_org_role_assignment_creates_org_member`: assigns `organization_admin` directly, asserts `OrganizationMember` exists and org appears in `OrganizationService.list()`.
- `test_direct_workspace_role_assignment_creates_workspace_and_org_member`: assigns `workspace_admin` directly, asserts both `WorkspaceMember` and `OrganizationMember` exist, org appears in list.

## Task: BUG-041 — Settings Pages "Access Restricted" for Users with Explicit Permissions

### Problem

Users with explicitly granted permissions on their role (e.g., `organization_member` role with `settings.member.view`) hit "Access Restricted" on all non-personal settings pages. The Members page was the main case.

### Root Cause

`settings/layout.tsx` gated ALL non-personal routes on role keys (`ORG_ADMIN_KEYS` etc.). Users not matching those keys were blocked before `can()` checks could run. `settings/members/page.tsx` had the same gate duplicated.

### Fix

**`frontend/src/app/settings/layout.tsx`**
- Removed `PERSONAL_ROUTES` constant and `usePathname` usage.
- Replaced the PERSONAL_ROUTES check + "Access Restricted" block with a single pass-through returning `authorityLevel: "member"` for all users without admin roles.
- Removed unused `SettingsEmptyState` / `SettingsPageLayout` import from this file.

**`frontend/src/app/settings/members/page.tsx`**
- Added a 4th query (`memberPermQuery`) that fires only when: no admin role found, queries resolved, user has any org/workspace assignment.
- The query calls `settingsApi.getCurrentPermissions` with the first found org/workspace scope.
- If `permission_codes` includes `settings.member.view`, renders `MembersView` scoped to that org/workspace.
- Loading state (`memberPermQuery.isLoading`) prevents premature "Access Restricted" display.

**`frontend/src/app/settings/organizations/[id]/page.tsx`**
- Added `can` to `usePlatformContext()` destructuring.
- Added `|| can("settings.organization.edit")` to `isAuthorized`.

**`frontend/src/app/settings/workspace/page.tsx`**
- Added `can` to `usePlatformContext()` destructuring.
- Added `|| can("settings.workspace.edit")` to `isAuthorized`.

### Verification

- `npm run build` — passed (TypeScript clean, no errors).

### Design Decision Added

`decisions.md`: Settings pages use `can()` for access/edit gates, never role keys. `authorityLevel` is kept for scope context only.

## Task: BUG-042 — Settings Pages Did Not Enforce Permission Hierarchy

### Problem

Settings pages checked each permission independently with flat `can()` calls. A child permission (e.g., `settings.member.invite`) could be checked without verifying its parent (`settings.member.view` + `settings.organization.view`) was also granted. The `workspaces/page.tsx` had no access gate at all (it was a trivial wrapper). `MembersView` action buttons (`canInvite`, `canChangeRoles`, `canRemoveMembers`) also used flat `permissions.can()` without chaining parents.

### Fix

**New file: `frontend/src/lib/settings-permissions.ts`**
- Created `hasHierarchicalPermission(can, ...permissions)` — returns `true` only when every permission in the chain is granted (`permissions.every(p => can(p))`).

**Admin bypass pattern** (consistent across all pages):
- `isAdminUser = isSuperuser || authorityLevel === "platform" || authorityLevel === "org"` — bypasses all hierarchy checks.
- `if (!isAdminUser && ctxIsLoading) return null;` — prevents premature "Access Restricted" during platform context load.

**`settings/organizations/page.tsx`**
- Added `canViewOrganizations = isAdminUser || hasHierarchicalPermission(can, "settings.organization.view")` gate with "Access Restricted" + `RequestAccessButton` return.

**`settings/organizations/[id]/page.tsx`**
- Added `canViewOrgPage` gate with hierarchy check.
- `isAuthorized` updated: `isAdminUser || hasHierarchicalPermission(can, "settings.organization.view", "settings.organization.edit")`.
- `OrgTabs` now accepts `hiddenTabs?: Set<string>` — filters tabs that the user lacks permission to see.
- Computes `hiddenTabs` from `canViewMembersTab` (`org.view + member.view`) and `canViewWorkspacesTab` (`org.view + workspace.view`).
- Danger zone gated on `isSuperuser || permissions?.roles?.some(r => r.key === "organization_owner")` (org owners + superusers only).

**`settings/workspaces/page.tsx`**
- Rewritten from trivial wrapper to full access-gated page.
- Gates on `isAdminUser || hasHierarchicalPermission(can, "settings.organization.view", "settings.workspace.view")`.

**`settings/workspace/page.tsx`**
- Added `canViewWorkspace` gate before the no-workspace check.
- `isAuthorized` updated to full chain: `isAdminUser || hasHierarchicalPermission(can, "settings.organization.view", "settings.workspace.view", "settings.workspace.edit")`.

**`settings-admin-views.tsx` (MembersView)**
- Added `import { hasHierarchicalPermission } from "@/lib/settings-permissions"`.
- `canInvite`, `canChangeRoles`, `canRemoveMembers` now use `hasHierarchicalPermission(permissions.can, "settings.organization.view", "settings.member.view", <action-code>)`.

### Verification

- `npm run build` — pending (see below)

### Design Decision Added

`decisions.md`: Permission hierarchy model documented. `hasHierarchicalPermission` is the canonical way to enforce parent→child permission chains in settings pages.

## Task: Visual Permission Editor — Phase 1 (God Mode Foundation)

### Scope

Frontend only. Build the PermissionGate component infrastructure for making permission-gated UI elements visible and editable in simulator edit mode.

### Files Created

**`frontend/src/components/platform/permission-gate.tsx`** (new)
- `PermissionGate({ permission, label, children, fallback?, className? })`
- Normal/View mode: `can(permission) ? children : fallback ?? null` — zero DOM overhead
- Edit mode: renders green ring + minus button on visible elements; dashed ghost placeholder + plus button on hidden elements
- Colour coding: green ring = stable visible, blue ring = pending addition, orange ghost = pending removal, gray ghost = always hidden
- Clicking +/- calls `markForAddition`/`markForRemoval` for instant preview, or `undoChange` if already pending

**`frontend/src/components/platform/visual-permission-editor.tsx`** (new)
- Floating save bar rendered at bottom of content area when `hasUnsavedChanges`
- Shows `+N permissions / -N permissions` counts
- Save: calls `listPermissions()` to resolve codes→IDs, then `addRolePermission`/`removeRolePermission` per change, then `commitChanges()` on success
- Discard: calls `clearPendingChanges()` — reverts `simulatedPermissions` to `originalSimulatedPermissions`

### Files Modified

**`frontend/src/lib/permission-simulator.ts`**
- Added `simulatedRoleId: number | null` (needed for save API calls)

- Updated `startSimulation` signature to include `roleId: number | null`
- `markForAddition` immediately adds to `simulatedPermissions` (instant preview); `markForRemoval` immediately removes
- `clearPendingChanges` (discard) reverts to `originalSimulatedPermissions`; `commitChanges` (after save) sets new baseline

**`frontend/src/layouts/asthra-shell.tsx`**
- Simulation banner now dynamic: amber in view mode, blue in edit mode
- Icon changes 👁→✏️ in edit mode; label changes "Simulating:" → "Editing permissions for:"
