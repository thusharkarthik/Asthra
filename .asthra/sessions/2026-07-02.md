# 2026-07-02 Session

## Organization Settings Scoped RBAC Gate

- Status: Implemented; frontend build passed.
- Root cause: `/settings/layout.tsx` could render the broad "Access Restricted" / Request Access state for `/settings/organizations` and `/settings/organizations/{id}` from the empty unscoped permission/authority state before organization-scoped context or permissions resolved. The routed organization page also mixed fallback platform-context permissions with route-scoped permissions and used archive/restore permissions as edit authority.
- Changes:
  - `frontend/src/app/settings/layout.tsx`: organization settings list/detail routes now bypass broad settings authority and let organization pages handle readiness/access.
  - `frontend/src/app/settings/organizations/[id]/page.tsx`: uses `GET /me/permissions?org_id=...` through `useCurrentPermissions({ orgId })`; shows loading/error/denied states explicitly; grants page access for `settings.organization.view`, `settings.organization.edit`, or `settings.organization.manage`; grants edit controls for `settings.organization.edit` or `settings.organization.manage`.
  - `frontend/src/components/settings/settings-admin-views.tsx`: organization edit action now checks `settings.organization.edit` or `settings.organization.manage`.
  - `frontend/src/hooks/use-platform-queries.ts`: scoped permission hook can be disabled for invalid/superuser route states.
- Backend: Not touched. HAR evidence already showed backend returning correct scoped permissions.
- Build: `cd frontend && npm run build` passed.
- Manual QA required: create organization, immediately open `/settings/organizations` and `/settings/organizations/{id}`, verify no false Request Access and edit controls are visible on detail; refresh the same routes; verify an unauthorized user still sees Request Access only after permission loading completes.

## Workspace/Project Settings Scoped RBAC Gate

- Status: Implemented; frontend build passed.
- Root cause: The Settings layout still made broad authority decisions for workspace/project settings routes, so `/settings/organizations/{id}/workspaces`, `/settings/workspaces`, `/settings/workspaces/{id}`, `/settings/workspaces/{id}/projects`, `/settings/projects`, and `/settings/projects/{id}` could be blocked before scoped permissions settled. Shared workspace/project views also showed limited-access states while the intended org/workspace/project permission query was still loading.
- Changes:
  - `frontend/src/app/settings/layout.tsx`: scoped settings route bypass now covers organization, workspace, and project list/detail settings routes.
  - `frontend/src/components/settings/settings-admin-views.tsx`: shared scoped permission hook can be disabled until a route scope exists; workspace/project list views show "Checking access" while scoped create permission loads; workspace/project detail views wait for scoped permissions and show Request Access only after scoped denial.
  - Workspace edit controls now use `settings.workspace.edit` or `settings.workspace.manage`.
  - Project edit controls now use `settings.project.edit` or `settings.project.manage`; archive/restore controls also accept `settings.project.manage`.
- Backend: Not touched.
- Build: `cd frontend && npm run build` passed.
- Manual QA required: from an organization detail page, open Workspaces and confirm no false Request Access; create workspace; open Projects and confirm no false Request Access; create project; refresh workspace/project list and detail routes; verify unauthorized users only see Request Access after scoped permission loading completes.
