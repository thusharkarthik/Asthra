## Task: Hard Reset Shows Onboarding Gate Instead of /login (BUG-043)

### Goal

Fix the bug where an expired/invalid token causes the app to show the onboarding gate instead of redirecting to `/login`. Root cause: stale `isAuthenticated=true` in localStorage bypasses the auth redirect effect; when platform context returns 401, `contextIsError=true` + `organizations=[]` makes `needsOnboarding=true`.

### Files Changed

- `frontend/src/layouts/asthra-shell.tsx` — 4 targeted changes:
  1. Added `isError: contextIsError, error: contextError` to `usePlatformContext()` destructure
  2. Added `!contextIsError` to `needsOnboarding` condition
  3. Added `useEffect` to call `logout()` when context returns 401 (clears all stores + redirects)
  4. Added synchronous `return null` guard (between context-loading gate and onboarding gate) to prevent rendering while redirect fires

### Guard Order After Fix

`public path` → `hydration/auth` → `context loading (initial)` → `401 null guard` → `onboarding gate`

### Edge Cases Verified (by design analysis)

1. No token (cleared localStorage): `isAuthenticated=false` → existing guard catches it ✓
2. Expired token → 401: new `contextIsError` effect + null guard catches it ✓
3. Valid new user, no org: `contextIsError=false`, `needsOnboarding=true` → onboarding gate ✓
4. Valid existing user: `contextIsError=false`, `organizations.length>0` → normal shell ✓
5. Public path: `isPublicPath=true` → effect skipped, guard skipped ✓

## Task: Fix Permission Registry Not Loading When God Mode Opens

### Root Cause

`isLoaded` persisted as `true` across logout → relogin within the same browser session (Zustand store is in-memory and not reset on logout). On re-login, when God Mode opened, the guard `!registryIsLoaded` was already `false`, so `loadRegistry` was never called.

Secondary risk: if `isSimulating` flipped to `true` while `isLoading` was transiently `true` from another trigger, no fallback existed to retry when the user clicked into Edit Mode.

### Files Changed

- `frontend/src/stores/permission-registry-store.ts` — Added `reset()` action that clears all state (`permissions`, `byModule`, `isLoading`, `isLoaded`, `error`, `lastSyncedAt`) back to initial values.
- `frontend/src/layouts/asthra-shell.tsx` — 4 changes:
  1. Added `resetRegistryFn` subscription (`usePermissionRegistryStore((s) => s.reset)`)
  2. 401 useEffect: calls `resetRegistryFn()` before `logout()` + added to dep array
  3. Added `isEditMode` fallback `useEffect` (same guard as `isSimulating` effect — fires when user enters Edit Mode in case `isSimulating` effect was blocked by transient `isLoading=true`)
  4. `handleLogout`: calls `resetRegistryFn()` before `logout()`

### Load Trigger Logic After Fix

```
God Mode opens (isSimulating: false → true)
  → useEffect fires
  → if (isSimulating && accessToken && !isLoaded && !isLoading) → loadRegistry()
  [if somehow blocked:]
User clicks Edit Mode (isEditMode: false → true)
  → fallback useEffect fires
  → same guard → loadRegistry()
  [on any logout/401:]
  → resetRegistryFn() clears isLoaded=true
  → next God Mode session loads fresh
```

## Task: Fix Permission Registry URL and Retry Loop

### Issues Fixed

**Fix 1 — Wrong URL (404)**: `loadRegistry` was calling raw `fetch("/api/core/api/v1/permissions/registry")` — a relative URL that resolves to the Next.js dev server (port 3000), not the backend (port 8080).

**Fix 2 — Retry loop on error**: After a failed load, `isLoaded=false` and `isLoading=false` remained, so the useEffect guards in the shell would keep calling `loadRegistry` on every re-render.

### Files Changed

- `frontend/src/stores/permission-registry-store.ts` — 3 changes:
  1. Added `import { settingsApi } from "@/services/api/settings-api"` — uses `apiRequest` → `apiConfig.gatewayUrl` (`NEXT_PUBLIC_API_GATEWAY_URL ?? "http://localhost:8080"`)
  2. Replaced raw `fetch(...)` with `settingsApi.listPermissionRegistry(token)` — correct base URL, typed return, consistent error handling via `ApiError`
  3. Added `hasAttempted: boolean` field (interface + initial state + `reset()`); set to `true` at the start of `loadRegistry`; added to the internal guard: `if (state.isLoaded || state.isLoading || state.hasAttempted) return;`

### State Machine After Fix

```
Initial:       isLoaded=false, isLoading=false, hasAttempted=false
Load starts:   isLoading=true,  hasAttempted=true
Success:       isLoaded=true,   isLoading=false  → guarded by isLoaded
Error:         isLoading=false, hasAttempted=true → guarded by hasAttempted (no retry)
reset():       all fields → false → next God Mode session loads fresh
```

## Task: Fix Sidebar Disappearing After Scope Auto-Selection (BUG-046)

### Root Cause

Backend `GET /context/platform` inferred `navigation_mode` from scope params (lines 60-64 of context.py):
```python
navigation_mode = "platform"
if org_id: navigation_mode = "org"
if workspace_id or project_id: navigation_mode = "work"
```

Frontend sent `workspace_id` (for permission scoping), backend returned work modules. Frontend sidebar called `buildNavSections("platform")` → no platform modules matched → empty `ModeNavSection[]`. Static fallback never triggered because `availableModules.length > 0` (work modules present).

### Files Changed

**Backend:**
- `services/core-service/app/api/v1/context.py` — Added `navigation_mode: str | None = Query(default=None)` param. Uses it when valid ("platform"/"org"/"work"); falls back to scope-based inference when absent.

**Frontend:**
- `frontend/src/services/api/core-api.ts` — Added `navigation_mode?: string` to `getPlatformContext` params type; appended to URL search params when present.
- `frontend/src/context/platformContext.tsx` — Added `useState<NavigationMode>` seeded from `auth-store.currentUser.is_superuser` (persisted). `useEffect` updates mode from roles after first context response. `navigationMode` included in `queryKey` (triggers refetch on mode change) and `queryFn` params.

### Mode Sharing Architecture

```
auth-store.currentUser.is_superuser
  → useState seed in PlatformContextProvider
  → contextQuery fires with navigation_mode param
  → data returns with roles
  → useEffect: detectNavigationMode(is_superuser, roles)
  → setState if mode changed → queryKey changes → refetch with correct mode
```

### First-Load Behavior

| User type | Seed | Extra call |
|---|---|---|
| Superuser | "platform" (from auth store) | None |
| Work member | "work" (default) | None |
| Org owner/admin | "work" → "org" (after roles load) | 1 extra call |

### Limitation

Superuser manual mode override (sidebar dropdown) does not update the context API's `navigation_mode`. The sidebar uses `effectiveNavigationMode` for `buildNavSections`, but `availableModules` remain platform-mode modules. Override falls back to static nav for non-platform modes (future work).

## Task: Fix Org Mode and Work Mode Sidebar Empty (BUG-046 follow-up)

### Root Cause

`navigationMode` seed was `is_superuser ? "platform" : "work"`. For non-superusers: seed = "work" → first context call returns work modules. Sidebar `effectiveMode` for an org owner is "org". `buildNavSections("org", workModules)` = [] (mode filter finds nothing). Static fallback never triggered because `availableModules.length > 0` was true. Empty sidebar.

### Files Changed (2)

- `frontend/src/context/platformContext.tsx` — Seed changed from `"work"` to `"platform"` for non-superusers. `CoreUser` has no `roles` field so seed is always either "platform" (superuser) or "platform" (everyone else, until roles arrive). This ensures the first context call fetches platform modules, which exist for all users with platform permissions. Org/work users trigger one refetch when roles arrive.

- `frontend/src/components/navigation/sidebar-nav.tsx` — Added two-step section resolution: `dynamicSections = buildNavSections(availableModules, effectiveMode)`, then `sections = dynamicSections.length > 0 ? dynamicSections : navSectionsForMode(effectiveMode)`. When dynamic modules are cached for a different mode (e.g., platform modules but mode is "org"), `buildNavSections` returns [] → static nav activates → sidebar shows correct items immediately.

### Behavior After Fix

| User | Seed | First load | After roles |
|---|---|---|---|
| Superuser | "platform" | Platform modules → sidebar ✓ | No refetch |
| Org owner | "platform" | Platform modules (wrong mode) → dynamic=[] → static org nav ✓ | Refetch with "org" → dynamic org modules |
| Work member | "platform" | Platform modules (wrong mode) → dynamic=[] → static work nav ✓ | Refetch with "work" → dynamic work modules |

Static nav guarantees non-empty sidebar at all times. Dynamic nav enhances it once correct modules are fetched.
