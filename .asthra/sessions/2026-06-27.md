## Bug Fix — Role Permission Checkbox Revert + Removal 404

**Branch**: `fix/role-permission-editing`

### Root cause

`addPermissionMutation.onSuccess` and `removePermissionMutation.onSuccess` both invalidated `["settings", "role-permissions", roleId]` BEFORE calling `invalidateSettingsAndContext`. The problem:

1. Role-permissions refetched → UI shows new permission as assigned ✓
2. `invalidateSettingsAndContext` → `["settings", "roles"]` refetched → `RoleService.list()` → `ensure_role_catalog()` → `_sync_role_template_permissions()` — may remove manually-added permission from DB for system roles whose template patterns don't include that permission
3. `rolePermissionsQuery` was already "fresh" (from step 1) → doesn't refetch → UI shows stale "Assigned" state
4. On next unchecked action: DELETE called → backend 404 ("Role permission link not found")

### Fix (`frontend/src/components/settings/settings-admin-views.tsx`)

**Invalidation order swapped** in both `onSuccess` callbacks:
```
before: role-permissions → invalidateSettingsAndContext
after:  invalidateSettingsAndContext → role-permissions
```

This ensures `ensure_role_catalog()` runs (and any backend permission sync completes) BEFORE `rolePermissionsQuery` refetches, so the UI always reflects the authoritative post-sync DB state.

**Optimistic updates added** to both mutations:
- `onMutate`: cancel in-flight queries, snapshot previous data, update cache immediately (instant visual feedback)
- `onError`: rollback cache to snapshot + show error toast
- `onSuccess`: general context first, then role-permissions confirm

## Fix 4 — Role-Permission Sync Made Additive Only (2026-06-28)

**Branch**: `fix/role-permission-editing`

### Problem
`_sync_role_template_permissions()` performed full reconciliation: computed wanted permissions from template patterns, then DELETE'd any DB entry not in the wanted set. This wiped every manual permission assignment made by admins. Template was being enforced as a permanent constraint rather than a starting seed.

Additionally, `ensure_role_catalog()` with `sync_permissions=True` (which runs the expensive permission catalog scan) was triggered on every `list()`, `list_templates()`, and `/me/permissions` API call — essentially on every page load in the settings UI.

### Files changed

**`services/core-service/app/services/role_service.py`**:
- Removed delete block from `_sync_role_template_permissions()`:
  - Gone: `for permission_id in existing_permission_ids - wanted_permission_ids: self.db.delete(mapping)`
  - Sync is now additive-only
- Updated early-exit: `existing_permission_ids == wanted_permission_ids` → `wanted_permission_ids.issubset(existing_permission_ids)`
- `list()`: `ensure_role_catalog()` → `ensure_role_catalog(sync_permissions=False)`
- `list_templates()`: same change

**`services/core-service/app/services/access_control_service.py`**:
- `ensure_role_catalog()` → `ensure_role_catalog(sync_permissions=False)` (called on every `/me/permissions` request)

**`services/core-service/app/api/v1/access_control.py`**:
- Added `from app.services.role_service import RoleService` import
- `sync_permission_registry()` endpoint: after `sync_registry_permissions()`, now also calls `RoleService(db).ensure_role_catalog(sync_permissions=False)` so the admin "Sync Permissions" button seeds role permissions too

### RBAC lifecycle after this fix
1. New service → permissions auto-generated
2. Permission Gap scanner detects missing permissions
3. "Generate Missing Permissions" adds to catalog
4. Permission Registry Sync → syncs catalog AND seeds role permissions (additive only)
5. Superuser reviews → manually assigns permissions to roles
6. Those assignments are permanent truth; sync never removes them
