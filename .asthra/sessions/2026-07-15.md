# 2026-07-15

## Core Navigation Registry v1

Audited existing navigation before implementation.

Findings:

- No backend Navigation Registry existed.
- Core Module Registry existed and already returned `modules` through Unified Platform Context.
- Frontend sidebar used `availableModules` via `buildNavSections()` as the dynamic source, then `navigation-mode.ts` static fallback.
- Sidebar permission visibility already used backend permission codes through `can(...)`.

Changes:

- Added `services/core-service/app/services/navigation_registry.py`.
- Added `services/core-service/app/schemas/navigation.py`.
- Added `services/core-service/app/api/v1/navigation.py` and registered it in the v1 router.
- Added `navigation` to `/api/v1/context/platform`.
- Added `settings.navigation.view` and `settings.navigation.manage` to the permission registry for future management UI.
- Added frontend `ResolvedNavigation` / `NavigationRegistryItem` types.
- Added `navigation` to frontend platform context with safe defaults.
- Updated sidebar source priority:
  1. Core Navigation Registry `navigation`
  2. Module Registry-derived `availableModules`
  3. Static fallback nav
- Kept existing sidebar UI and static fallback behavior.

Validation:

- `cd services/core-service && pytest tests/test_navigation_registry.py -vv` passed.
- `cd services/core-service && pytest tests/test_app_imports.py -vv` passed.
- `cd frontend && ./node_modules/.bin/tsc --noEmit` passed.

Notes:

- Navigation Registry controls visibility/placement only. Backend permissions and route/page guards remain authoritative.
- No sidebar customization UI was built.
