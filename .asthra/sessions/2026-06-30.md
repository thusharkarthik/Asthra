## Task: Core Migration 0013 Duplicate role_assignments Unblocker

### Issue

Core failed during Alembic startup at `0012_access_control_foundation -> 0013_scoped_membership_foundation` with:

`sqlite3.OperationalError: table role_assignments already exists`

Because Core failed startup, gateway login requests returned `502 Bad Gateway`.

### Root Cause

`0013_scoped_membership_foundation.py` unconditionally created `role_assignments`, `project_memberships`, their indexes, and `team_members.status/joined_at`. In local SQLite dev databases, Core bootstrap/model metadata can create missing model tables before Alembic reaches 0013, leaving the database with `role_assignments` already present while the Alembic version remains before 0013.

### Fix

- Added Alembic inspector helpers to `0013_scoped_membership_foundation.py`.
- Guarded `op.create_table` for `role_assignments` and `project_memberships`.
- Guarded index creation for both tables.
- Guarded `team_members` column/index additions.
- Kept RBAC architecture unchanged: `role_assignments` remains the source of truth; no `user_roles` usage added.

## Task: Idempotent Alembic Migrations — Permanent Fix

**Problem**: Two consecutive migrations (0013, 0014) crash-looped with "table already exists" because `alembic_version` was behind the actual DB schema. Every future migration creating a table or index faced the same risk.

**Root cause pattern**: SQLite dev volumes can have tables created through `create_all()` or partial migration runs, leaving `alembic_version` behind the actual schema state. Alembic retries the failed migration on every startup → crash loop.

**Fix**: Created `services/core-service/app/db/migration_utils.py` with three shared helpers (`table_exists`, `index_exists`, `column_exists`). Retrofitted all 9 migrations that contain `op.create_table` or `op.create_index`:

- **0001** — 11 tables, 20 indexes guarded
- **0005** — project_teams table + index guarded
- **0006** — role_permissions, user_roles tables + indexes guarded
- **0008** — invitations table + indexes guarded
- **0010** — notifications table + index guarded
- **0011** — api_keys table + indexes guarded
- **0013** — already guarded (inline helpers replaced with shared helper for consistency)
- **0014** — feature_flags, feature_flag_overrides tables + indexes guarded (was the active blocker)
- **0015** — module_registry table + indexes guarded

**Import path**: `from app.db.migration_utils import table_exists, index_exists, column_exists` — resolves correctly because `/app` is on sys.path in the container (proven by env.py using the same pattern).

**Double-upgrade test**: Passed. First run applied 0014 + 0015 cleanly. Second run was a silent no-op (`already at head`).

**Service verification**:
- core-service restarts cleanly: `Uvicorn running on http://0.0.0.0:8000`
- Login returns `"Invalid email or password."` — not 502

**Image note**: `alembic/versions/` is baked into the Docker image (not bind-mounted), so migrations require `docker compose build core-service` after any change.
