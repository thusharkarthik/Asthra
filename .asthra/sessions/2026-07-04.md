## Task 10 — God Mode Bug Fixes [COMPLETED]

**Goal**: Fix two God Mode issues found during QA.

**Fix 1 — Edit mode not activating PermissionGate overlays**:
Root cause: `activateGodMode` originally set `isSimulating: true` only inside a 1800ms `setTimeout`, meaning `isSimulating` was `false` when the toolbar appeared and the user clicked Edit. `PermissionGate` guards on `isSimulating && isEditMode`, so overlays never rendered.

Fix: restructured `activateGodMode` in `permission-simulator.ts` to set `isSimulating: true` and all role data **immediately** (synchronously). The `setTimeout` now only flips `isActivating → false` and `isGodModeReady → true`. Side benefit: overlay animation now shows the role name correctly (was showing blank before).

**Fix 2 — Role switcher in toolbar**:
Added inline role-switcher dropdown to `GodModeToolbar`:
- Loads all active non-superuser roles via `settingsApi.listRoles` on mount
- `<select>` replaces the static role name display
- On change: calls `settingsApi.simulatePermissions` → `startSimulation` (no animation; `isGodModeReady` stays `true`)
- Shows "Switching…" text during fetch
- Falls back to static role name while roles load; shows current role if excluded from list (e.g. superuser)

**Files changed**:
- `frontend/src/lib/permission-simulator.ts` — `activateGodMode` restructured (see Fix 1 above)
- `frontend/src/components/platform/god-mode-toolbar.tsx` — Added `useEffect` roles loader, `handleRoleSwitch`, role `<select>` dropdown; added `roleKeyToNavigationMode` + `RoleRecord` imports

**Build**: Passed.

## Task 13 — God Mode Auto-Overlay: Tracked can() System [COMPLETED]

**Goal**: Replace manual PermissionGate wrapping with a tracked can() system that automatically detects every permission-gated component and surfaces controls in God Mode edit mode. Zero extra developer work, 100% future coverage.

**Core insight**: Every permission-gated component already calls `can("code")`. In God Mode edit mode, make `can()` also register that check in a Zustand tracker store. A panel reads the tracker and renders +/- controls for all detected permissions.

**Architecture**:
- `frontend/src/lib/god-mode-tracker.ts` (new) — Lightweight Zustand store. Tracks `Record<code, { code, route }>`. Deduplicates: same code + route = no-op (returns existing state → no subscriber re-renders).
- `frontend/src/context/platformContext.tsx` — `can()` calls `useGodModeTracker.getState().registerPermissionCheck(code, pathnameRef.current)` when `isGodModeReady && isEditMode`. Key patterns: `getState()` (no subscription from provider), `pathnameRef` (current pathname without adding it to useMemo deps). Added `isEditMode` subscription + useMemo dep.
- `frontend/src/components/platform/god-mode-auto-overlay.tsx` (new) — `fixed right-4 top-20 z-50 w-72` panel. Filters tracker by current pathname. Computes `granted` from `simulatedPermissions` (always reactive). +/- buttons call `markForAddition`/`markForRemoval`/`undoChange`.
- `frontend/src/layouts/asthra-shell.tsx` — Imports + mounts `<GodModeAutoOverlay />`. Two effects: `clearForRoute(pathname)` on navigation, `clearAll()` when `!isGodModeReady`.
- `frontend/src/components/platform/permission-gate.tsx` — JSDoc note: new code should prefer `can()` directly; PermissionGate kept for explicit wrapping.

**Coverage**: Was 41 manually-wrapped permissions. Now any of 313 backend permissions trackable automatically. New components using `can()` get coverage with zero extra work.

**Convention going forward**: `{can("code") && <Component />}` preferred over `<PermissionGate>` for new code.

**Build**: Passed (`npm run build` exit code 0).

## Task 11 — OpenAPI Client Generation: Fix predev/prebuild blocking [COMPLETED]

**Goal**: Fix two issues preventing the frontend container from starting: (1) `predev`/`prebuild` exiting non-zero when generation fails, blocking the dev server; (2) `@hey-api/openapi-ts` binary missing from the Docker named volume.

**Root cause analysis**:
- `openapi-ts.config.ts` points to `http://localhost:8000/openapi.json`. Inside the Docker container, `localhost` resolves to the container itself — not `asthra-core-service`. Generation always fails in the container.
- The named volume `asthra_frontend_node_modules` predated the `@hey-api/openapi-ts` devDependency being added. Docker copies image node_modules to the volume on first start only; subsequent starts reuse the existing (stale) volume.
- Combined: `npm run dev` → `predev` → `openapi-ts` → "not found" → non-zero exit → container exits.

**Fix 1** — `frontend/package.json`:
```
"prebuild": "npm run generate:api || true"
"predev":   "npm run generate:api || true"
```
Generation failure is now non-fatal. Dev server and production build proceed using the last successfully generated files.

**Fix 2** — Docker volume update:
```bash
docker compose run --rm frontend sh -c "npm install"
```
Ran `npm install` inside a temporary container sharing the named volume. Binary `openapi-ts` confirmed present in `/app/node_modules/.bin/` afterwards.

**Dockerfile**: No changes needed. The `deps` stage already runs `npm ci` without `--only=production`, which correctly includes all devDependencies. The volume staleness issue is a one-time fix; future image rebuilds repopulate the volume from scratch.

**Outcome**:
- Frontend container starts cleanly (`✓ Ready in 9.2s`)
- `predev` runs → generation fails with "fetch failed" (expected) → `|| true` → Next.js starts
- `npm run build` passes

**Files changed**: `frontend/package.json` (2-line diff)
