## Task: Fix Broken Shell Layout After Unified Context API Migration

**Bug**: Shell rendered with broken layout (oversized logo, empty sidebar, collapsed footer dock) on first load after the unified platform context API migration.

**Root cause**: The old multi-query setup had `useCurrentUser()` seeded with `initialData` from the auth Zustand store, making `isLoading` go false almost immediately. The new single unified `contextQuery` has no `initialData`, so `isLoading=true` until the full `/context/platform` response returns. The shell's existing early-return gates only checked `!hasHydrated || !isAuthenticated` — nothing blocked the full shell DOM from rendering while `contextLoading=true`. During that window: `organizations=[]`, `permissions=null`, footer switchers rendered empty, sidebar nav empty — the flex layout collapsed and the logo dominated visually.

**Fixes**:

**`context/platformContext.tsx`**:
- Added `keepPreviousData` import from `@tanstack/react-query`
- Added `placeholderData: keepPreviousData` to the `useQuery` options — prevents `isLoading` from re-firing when scope changes (org/workspace/project switch changes the queryKey; without this the entire shell would flash to loading screen on every scope change)

**`layouts/asthra-shell.tsx`**:
- Extracted `AppLoadingScreen({ label })` local component (reused for both auth gate and context gate — consistent loading UI)
- Added `contextLoadedAt` from `usePlatformContext()` (the `loadedAt` field, set once on first successful fetch, never reset)
- Added gate after the auth check: `if (contextLoading && !contextLoadedAt) return <AppLoadingScreen label="Loading your workspace..." />;`
- Gate fires only on true first load (no cached data yet); subsequent background refetches keep `contextLoadedAt` truthy so they don't re-trigger the blocking screen

**Why `loadedAt` instead of `contextQuery.data`**: We don't have direct access to `contextQuery` in the shell, only the context value. `loadedAt` is already part of `PlatformContextValue`, set on first successful data arrival and persistent across query key changes — exactly the right signal.

**Symptom**: `asthra-core-service` crash-looping on startup with `sqlalchemy.exc.OperationalError: table role_assignments already exists` when running migration `0013_scoped_membership_foundation`.

**Root cause**: `alembic_version` table recorded last applied migration as `0012_access_control_foundation`, but the database already contained all tables from 0013 (`role_assignments`, `project_memberships`) and beyond — 5 live rows in `role_assignments`. The schema and `alembic_version` were out of sync. Alembic tried to re-run 0013 upgrade which crashed on `CREATE TABLE role_assignments`.

**Diagnosis**:
- `docker` not available directly in WSL2 distro (Desktop integration disabled)
- Found `/var/run/docker.sock` accessible via `DOCKER_HOST=unix:///var/run/docker.sock`
- Used `docker run --rm -v asthra_core_service_data:/app/data` to run Python against the SQLite DB without starting core-service
- Confirmed: `alembic_version = [('0012_access_control_foundation',)]`, `role_assignments` has 5 rows, all 0013 tables present

**Fix**: Stamped migration 0013 as applied (no SQL executed, only updates `alembic_version`):
```bash
DOCKER_HOST=unix:///var/run/docker.sock docker run --rm \
  -v asthra_core_service_data:/app/data \
  -v ./services/core-service/app:/app/app \
  -e DATABASE_URL=sqlite:////app/data/asthra_core.db \
  asthra-core-service \
  sh -c "cd /app && alembic stamp 0013_scoped_membership_foundation"
```

**Verified**: `alembic current` → `0013_scoped_membership_foundation (head)`.

**Restart**: `DOCKER_HOST=unix:///var/run/docker.sock docker compose up -d` — all 18 containers Up, core-service starts Uvicorn successfully.

**No data loss**: `role_assignments` preserved (5 rows intact). No tables dropped or modified.
