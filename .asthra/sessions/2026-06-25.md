### Fix 1 — page.tsx: Remove bottom-bar dependency

Rewrote `MembersSettingsPage` to derive scope from user authority:
- Reads `currentUser.is_superuser` from auth store (synchronous, no API)
- Fetches platform-scope permissions via `settingsApi.getCurrentPermissions(token, {})` directly (bypassing the hook that falls back to store selections)
- Fetches `listRoleAssignments({ user_id, status: "active" })` for current user
- Cross-references with `listRoles()` to map `role_id → role.key`
- Authority priority: superuser → platform admin → org admin → workspace admin → default global

### Fix 2 — settings-admin-views.tsx: Remove silent org fallback

`scopeOrganizationId` previously fell back to `organizations[0]?.id`, silently targeting the wrong org in global directory mode. Changed to `null`. Existing `!scopeOrganizationId` guard now fires correctly. Error message updated to be actionable.

### Fix 3 — settings-admin-views.tsx: Guard workspaceId in queryFn

Added `if (!workspaceId) return [];` inside `membersQuery.queryFn` so `listWorkspaceMembers` is never called with ID 0, even if the `enabled` guard is bypassed by a race or future refactor.

## Key Discoveries

- `useCurrentPermissions` hook cannot force platform scope by passing `null` — `null ?? selectedOrganizationId` evaluates to `selectedOrganizationId`. Must call `settingsApi.getCurrentPermissions(token, {})` directly.
- `RoleAssignmentRecord` has `role_id` but NOT `role_key`. Cross-referencing with `listRoles()` is required.
- Platform-scope `/me/permissions` only returns `UserRole` rows + `RoleAssignment` rows where `scope_type="platform"`. Org/workspace admin roles are invisible at platform scope.
- No existing tests render `MembersSettingsPage` — all tests render `MembersView` directly with explicit props.

## Session 2026-06-25 (second pass)

### Settings Members Page: Remove Default Global Directory Fallback (BUG-004)

**Root cause**: The authority resolution chain in `page.tsx` ended with `return <MembersView />` (global directory, no props) as the default catch-all. Any authenticated user who had no admin role — including a brand new registrant — would land in global directory mode, which calls `listUsers` and shows all platform users.

**File changed**: `frontend/src/app/settings/members/page.tsx` only.

**Change**: Added import for `SettingsEmptyState` and `SettingsLayout` from `settings-components.tsx`. Replaced the final `return <MembersView />` with a `SettingsLayout` + `SettingsEmptyState` block showing "Access Restricted" / "You don't have permission to view or manage members." No `MembersView` instance is created, so no member-list API calls fire.

**Authority resolution (final state)**:
1. `is_superuser` → `<MembersView />` (global directory)
2. Loading → `null`
3. Platform admin role in platform-scope permissions → `<MembersView />` (global directory)
4. Org admin/owner role assignment → `<MembersView organizationId={N} />`
5. Workspace admin/manager role assignment → `<MembersView workspaceId={N} />`
6. No match → `SettingsLayout` + `SettingsEmptyState` ("Access Restricted")

### Settings Route Guard + /settings/members/:id Auth Fix (BUG-005, BUG-006)

**Files created/changed**:
- `frontend/src/app/settings/layout.tsx` — CREATED
- `frontend/src/app/settings/members/[id]/page.tsx` — REWRITTEN

**Root causes**:
- BUG-005: `members/[id]/page.tsx` was a 5-line server component with no auth check. Any authenticated user hitting `/settings/members/15` saw full user profile + roles + permissions.
- BUG-006: No `layout.tsx` existed under `/settings/`. All admin settings routes were unguarded — any authenticated user could navigate directly to any settings page.

**`settings/layout.tsx` (new)**:
- Central auth guard wrapping all `/settings/*` routes
- Unauthenticated → redirect to `/login` (belt-and-suspenders; AsthraShell also handles this)
- Superuser / platform admin → full access
- Org admin/owner / workspace admin/manager → full access
- No authority: only `/settings`, `/settings/profile`, `/settings/preferences`, `/settings/notifications`, `/settings/account` are allowed; everything else → "Access Restricted"
- Uses same TanStack Query keys as `members/page.tsx` → one cached network fetch serves layout + page

**`members/[id]/page.tsx` (rewritten)**:
- Converted from server component to client component (`"use client"`)
- Uses `useParams()` to read `id` from route
- Same 3-query authority resolution as `members/page.tsx` (shared cache via same query keys)
- No admin authority → "Access Restricted" state, `MemberDetailView` never instantiated
