# Permission Registry Engine

Asthra permissions are generated from a registry instead of guessed one by one.

## Permission Format

Permissions use:

```text
module.resource.action
```

Examples:

- `settings.project.restore`
- `settings.team.edit`
- `flow.work_item.transition`
- `docs.page.publish`

## Registry Model

Each registry item defines:

- module
- resource
- action
- scope
- risk level
- generated code
- generated name
- generated description

Core syncs registry permissions into the `permissions` table on startup. Missing permissions are created. Existing registry permissions have metadata refreshed. Custom permissions are preserved.

## Lifecycle

- `source=registry`: generated by the registry.
- `source=custom`: manually created custom permission.
- `status=active`: usable in role mappings and enforcement.
- `status=inactive`: intentionally disabled.
- `status=deprecated`: no longer part of the registry, but retained for audit and compatibility.

## Role Mapping Strategy

Users never receive permissions directly.

Users receive roles at a scope. Roles contain permissions.

System role templates map to registry permissions using wildcard patterns such as:

- `settings.project.*`
- `settings.team.*`
- `flow.work_item.*`

This means new action permissions become available to the right system roles after registry sync and role template sync.

## Owner QA Permissions

Organization Owner receives organization-scoped operational permissions, including:

- `settings.project.create`
- `settings.project.edit`
- `settings.project.archive`
- `settings.project.restore`
- `settings.team.create`
- `settings.team.edit`
- `settings.team.delete`
- `settings.team.member.add`
- `settings.team.member.remove`

These inherit through organization to workspace and project scope.

## Permission Gap Detection

Core exposes registry and gap views:

- `GET /api/v1/permissions/registry`
- `GET /api/v1/permissions/gaps`

Gaps identify registry permissions that are missing, inactive, or deprecated.

## Adding New Actions

1. Add the resource/action to `services/core-service/app/services/permission_registry.py`.
2. Use the generated permission code in backend enforcement.
3. Use the same permission code in frontend visibility checks.
4. Confirm system role patterns grant it to the right roles.
5. Add tests for owner/admin/viewer behavior.
